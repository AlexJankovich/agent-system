# AGENTS.md

Этот файл — инструкция для ИИ-агентов (OpenCode v2) при работе с кодом
в этом репозитории. Публикация изменений — через **GitHub** (`gh` CLI).

> Русская версия: этот файл.

## Обзор репозитория

Библиотека скиллов, ролей агентов и команд оркестрации для интеграции
ИИ-ассистентов в процесс веб-разработки. Компоненты живут в `.opencode/`
и разделены на три компонуемых слоя (см. «Оркестрация» ниже).

## Ограничения архитектуры

Репозиторий не определяет собственных runtime-пакетов. Все компоненты —
это декларативные файлы (Markdown, JSONC), интерпретируемые OpenCode.

## Интеграция агентов

ИИ-агенты работают по модели **skill-driven execution**, построенной на
инструменте `skill` и директориях `.opencode/skills/` и
`.opencode/agents/`.

### Ключевые правила

- Если задача соответствует какому-либо скиллу — ты **обязан** его
  вызвать.
- Скиллы лежат по пути `.opencode/skills/<skill-name>/SKILL.md`.
- Никогда не реализуй задачу напрямую, если применим скилл.
- Всегда следуй workflow скилла полностью (никогда частично).
- Primary-агент (`build`) делегирует субагентам через инструмент
  `subagent`; субагенты не могут запускать других субагентов.

### Intent → Skill Mapping

- Новый проект, крупная фича, неясные требования → `spec-driven-development`
- Новая функциональность в рамках существующей спеки → `planning-and-task-breakdown`, затем `incremental-implementation`, `tdd`
- Планирование / декомпозиция → `planning-and-task-breakdown`
- Баг / сбой / неожиданное поведение → `debugging-and-error-recovery`
- Ревью кода → `code-review`
- UI-работа → `frontend-ui-engineering`
- Рефакторинг / упрощение → `code-review` (рефакторинг в REVIEW)
- Публикация изменений (коммиты, ветки, PR) → `pull-request`
  (загружает `git-conventions` первым шагом)
- Настройка CI/CD → `ci-cd-and-automation`

**Периферийные скиллы** — вне основного цикла. Вызывай только по
явному запросу:

- `qa` — разговорный приём багов → GitHub issues (через `gh`)
- `humanizer` — удаление ИИ-паттернов из текста
- `dnote` — личные заметки

### Lifecycle Mapping

Слэш-команды для внутренних фаз жизненного цикла (`/spec`, `/plan`)
агенты не предоставляют — эти фазы идут автоматически. Однако
пользователь может явно вызвать команду верхнего уровня (например,
`/review-loop`, `/agent-loop`); в этом случае команда переопределяет
авто-детекцию.

Внутренний жизненный цикл:

- DEFINE → `spec-driven-development` (для крупных задач) или
  `context-builder` (для сбора контекста в `agent-loop`).
  Опционально `oracle` — проверка согласованности с унаследованными
  решениями.
- PLAN → `planning-and-task-breakdown`
- BUILD → `incremental-implementation` + `tdd`
- VERIFY → `debugging-and-error-recovery`
- REVIEW → `code-review`
- SHIP → `pull-request` + `ci-cd-and-automation`

**Для мелких задач.** Не запускай SDD для однострочных правок,
исправления опечаток и тривиальных изменений. Минимальная планка для
крупного скилла — задача, которая затрагивает несколько модулей, требует
архитектурного решения или займёт больше одной сфокусированной сессии.

Для фич, охватывающих несколько слайсов, предпочитай скилл
`agent-loop`. Он проводит весь жизненный цикл с двумя точками одобрения
пользователем (план, публикация) и обеспечивает ревью на уровне фичи.

### Модель исполнения

Для каждого запроса:

1. Определи, применим ли какой-либо скилл (даже с вероятностью 1%).
2. Вызови соответствующий скилл через инструмент `skill`.
3. Строго следуй workflow скилла.
4. Переходи к реализации только после завершения обязательных
   предшествующих шагов (спецификация, план и т. д.).

### Антирационализация

Следующие мысли некорректны и должны игнорироваться:

- «Эта задача слишком мала для скилла.»
- «Я могу быстро реализовать это сам.»
- «Сначала соберу контекст, потом подумаю о скилле.»

Правильное поведение: всегда сначала проверяй и используй скиллы.

## Оркестрация: роли, скиллы и команды

Три компонуемых слоя:

- **Скиллы** (`.opencode/skills/<name>/SKILL.md`) — workflow. Отвечают
  на вопрос *«Как?»*.
- **Роли** (`.opencode/agents/<role>.md`) — персоны. Отвечают на
  вопрос *«Кто?»*.
- **Slash-команды** (`.opencode/commands/<command>.md`) — точки входа.
  Отвечают на вопрос *«Когда?»*.

**Правило композиции:** `build` — primary-агент и единственный
оркестратор. Он запускает субагентов через инструмент `subagent`. Роли
никогда не запускают другие роли. Роль может загружать скиллы через
инструмент `skill`.

Единственный одобренный паттерн многоагентной оркестрации —
**параллельный fan-out с этапом слияния** (используется в
`/parallel-review` и `/parallel-research`), который `build` выполняет
двумя вызовами `subagent` в одном сообщении.

Субагенты не могут связаться с родителем во время выполнения. Если
субагент заблокирован, он возвращает блокирующий вопрос в финальном
ответе; `build` читает его и либо решает сам, либо задаёт вопрос
пользователю через инструмент `question`.

Не создавай «router»-роль. Оркестратор — `build`.

## Публикация (GitHub)

Публикация автоматизируется скиллом `pull-request`. Он загружает
`git-conventions` первым шагом, затем:

- создаёт feature-ветку по правилам именования,
- формирует сообщение коммита в формате Conventional Commits,
- выполняет `git push` и `gh pr create` с шаблоном PR.

Оба скилла — `pull-request` и `git-conventions` — лежат в
`.opencode/skills/`. `git-conventions` — самостоятельный скилл, потому
что правила веток и коммитов также используются `worker` (атомарные
коммиты) и `reviewer` (контекст диффа).

## Создание нового скилла

### Структура директории

```
.opencode/skills/
  {skill-name}/
    SKILL.md              # Обязательно
    scripts/              # Опционально: исполняемые помощники
      {script-name}.sh
    references/           # Опционально: progressive-disclosure
      {reference-name}.md
```

### Соглашения об именовании

- **Директория скилла**: `kebab-case`.
- **SKILL.md**: всегда заглавными, всегда именно это имя файла.
- **Скрипты**: `kebab-case.sh`.
- **Файлы references**: `kebab-case.md`.

### Формат SKILL.md

```markdown
---
name: {skill-name}
description: {Одно предложение с триггерами «Use when...».}
---

# {Skill Title}

{Обзор.}

## How It Works

{Нумерованный workflow.}

## Output

{Пример.}

## Verification

{Чек-лист.}
```

### Эффективность контекста

- Держи SKILL.md **до 500 строк** — детали выноси в `references/`.
- Пиши **конкретные `description`** — по ним агент выбирает скилл.
- Используй **progressive disclosure** — ссылайся на файлы в
  `references/`, загружай их только при необходимости.
- Ссылки идут **на один уровень вглубь** — из SKILL.md прямо в
  `references/`.
- **Предпочитай скрипты inline-коду** — запуск скрипта не потребляет
  контекст.

### Требования к скриптам

- Shebang `#!/bin/bash`.
- `set -e`.
- Статусные сообщения в stderr: `echo "..." >&2`.
- Машиночитаемый вывод (JSON) в stdout.
- Trap для очистки временных файлов.

## Чек-лист агента

- [ ] Все применимые скиллы вызваны.
- [ ] Workflow каждого скилла соблюдён полностью.
- [ ] Код не написан в фазах, где это запрещено (DEFINE, PLAN, REVIEW).
- [ ] Соответствие `git-conventions` проверено перед коммитом.
- [ ] Не осталось мёртвого кода, заглушек или временных логов.
