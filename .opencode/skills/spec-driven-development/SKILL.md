# Разработка на основе спецификаций

## Обзор

Пиши структурированную спецификацию перед написанием любого кода.
Спецификация — общий источник истины между тобой и человеком-
разработчиком. Она определяет, что мы создаём, зачем и как поймём, что
задача выполнена. Писать код без спецификации — это гадание.

## Когда использовать

- Запуск нового проекта или крупной фичи.
- Требования двусмысленны, неполны или существуют только как идея.
- Изменение затрагивает несколько файлов или модулей.
- Принимается архитектурное решение с долгими последствиями.
- На реализацию уйдёт больше одной сфокусированной сессии (>30 минут).

## Когда НЕ использовать

- Правки в одну строку.
- Исправление опечаток.
- Изменения, где требования однозначны и самодостаточны.
- Задачи, где уже есть утверждённый план (`tasks/plan.md`).
- Стандартная работа в `agent-loop` — спецификация заменяется
  планированием и контекстом.

**Для средних задач** (несколько файлов, но без архитектурных
последствий) — используй **облегчённый вариант** (см. ниже), а не
полный SDD.

## Полный рабочий процесс (для крупных задач)

Четыре этапа. Не переходи к следующему, пока не утверждён текущий.

```
СПЕЦИФИКАЦИЯ → ПЛАН → ЗАДАЧИ → РЕАЛИЗАЦИЯ
      │          │        │           │
      ▼          ▼        ▼           ▼
  Проверка   Проверка  Проверка   Проверка
  человеком  человеком человеком  человеком
```

### Этап 1 — Спецификация

Начни с общего видения. Задавай уточняющие вопросы, пока требования
не станут конкретными.

**Сразу выявляй предположения.** Перед написанием спецификации
перечисли то, что предполагаешь:

```
МОИ ПРЕДПОЛОЖЕНИЯ:
1. Это веб-приложение (не нативное мобильное)
2. Аутентификация на cookie-сессиях (не JWT)
3. База данных — PostgreSQL (по существующей схеме Prisma)
4. Поддерживаем только современные браузеры (без IE11)
→ Поправь меня сейчас, или продолжу с этими предположениями.
```

Не заполняй неясные требования молча. Главная цель спецификации —
выявить недопонимание **до** написания кода.

**Спецификация покрывает шесть областей:**

1. **Цель (Objective)** — что создаём и зачем. Кто пользователь? Как
   выглядит успех?
2. **Команды (Commands)** — полные исполняемые команды с флагами.
   ```
   Сборка: npm run build
   Тесты:  npm test -- --coverage
   Линтер: npm run lint --fix
   Dev:    npm run dev
   ```
3. **Структура проекта (Project Structure)** — где живёт исходный
   код, куда класть тесты и документацию.
4. **Стиль кода (Code Style)** — один реальный фрагмент кода лучше
   трёх абзацев описания. Соглашения об именовании, правила
   форматирования, примеры качественного вывода.
5. **Стратегия тестирования (Testing Strategy)** — библиотека, где
   лежат тесты, требования к покрытию, уровни для разных задач.
6. **Границы (Boundaries)**:
   - **Всегда:** запускай тесты перед коммитами, следуй соглашениям об
     именовании, валидируй вход.
   - **Сначала спроси:** изменения схемы БД, добавление зависимостей,
     изменение конфигурации CI.
   - **Никогда:** коммитить секреты, редактировать vendor-директории,
     удалять упавшие тесты без одобрения.

**Шаблон спецификации:**

```markdown
# Спецификация: [Название проекта/фичи]

## Цель
[Что создаём и зачем. Пользовательские сценарии или критерии приёмки.]

## Технологический стек
[Фреймворк, язык, ключевые зависимости с версиями.]

## Команды
[Сборка, тесты, линтер, запуск — полные команды.]

## Структура проекта
[Директории с описанием.]

## Код-стайл
[Пример кода + ключевые соглашения.]

## Стратегия тестирования
[Фреймворк, расположение тестов, покрытие, уровни.]

## Границы
- Всегда: [...]
- Сначала спроси: [...]
- Никогда: [...]

## Критерии успеха
[Конкретные проверяемые условия.]

## Открытые вопросы
[Всё, что не решено и требует участия человека.]
```

**Формулируй инструкции как критерии успеха.** Неточные требования
переводи в конкретные условия:

```
ТРЕБОВАНИЕ: «Сделай дашборд быстрее»

ПЕРЕФОРМУЛИРОВАННЫЕ КРИТЕРИИ УСПЕХА:
- LCP дашборда < 2.5 с на 4G.
- Первичная загрузка данных < 500 мс.
- CLS < 0.1.
→ Верны ли эти целевые показатели?
```

### Этап 2 — План

После утверждения спецификации составь технический план:

1. Основные компоненты и зависимости.
2. Порядок реализации (что строить первым).
3. Риски и стратегии их снижения.
4. Задачи, которые можно распараллелить, и последовательные.
5. Контрольные точки между этапами.

План должен быть удобен для ревью: человек читает и говорит «Да, это
правильный подход» или «Нет, измени X».

**Результат этапа** — `tasks/plan.md`. Если работа пойдёт через
`agent-loop`, дальше загрузится `planning-and-task-breakdown`; если
нет — составляй `tasks/todo.md` вручную по шаблону ниже.

### Этап 3 — Задачи

Разбей план на отдельные готовые к реализации задачи:

- Одна задача — одна сфокусированная сессия.
- У каждой — чёткие критерии приёмки.
- У каждой — шаг проверки (тест, сборка, ручная проверка).
- Порядок — по зависимостям, а не по важности.
- Задача не должна требовать изменения более ~5 файлов.

**Шаблон задачи:**

```markdown
- [ ] Задача: [Описание]
  - Приёмка: [Что должно быть выполнено]
  - Проверка: [Команда теста / сборка / ручная проверка]
  - Файлы: [Какие файлы будут изменены]
```

**Результат этапа** — `tasks/todo.md`.

### Этап 4 — Реализация

Выполняй задачи по одной:

- `incremental-implementation` — построение по одному вертикальному
  слайсу.
- `tdd` — цикл red → green внутри слайса.
- Ссылка на спеку в PR — давай ссылку на раздел спецификации, который
  реализует PR.

Если работа идёт через `agent-loop` — фазы 2–4 `agent-loop`
заменяют этот шаг.

## Облегчённый вариант (для средних задач)

Если задача затрагивает несколько файлов, но не имеет архитектурных
последствий, не пиши полную спеку. Зафиксируй **три пункта** и
предъяви их пользователю:

```markdown
## Мини-спека: [Название]

### Цель
[Одно-два предложения.]

### Критерии успеха
- [Конкретное, проверяемое условие.]
- [Конкретное, проверяемое условие.]

### Границы
- Не трогаем: [список областей вне scope.]
```

Этого достаточно для согласования и не превращается в «код, написанный
прозой».

## Связь с другими скиллами

- `planning-and-task-breakdown` — следующий шаг после утверждения
  спецификации.
- `agent-loop` — предпочтительный маршрут для многослайсовых фич.
  Если запускаешь `agent-loop`, спецификация служит входом для Фазы 1
  (контекст + план).
- `incremental-implementation` и `tdd` — реализация.
- `code-review` — ревью на уровне диффа.
- `pull-request` и `git-conventions` — публикация.

## Поддержание спецификации в актуальном состоянии

Спецификация — живой документ, а не одноразовый артефакт:

- **Обновляй при изменении решений** — сначала правь спецификацию,
  потом код.
- **Обновляй при изменении scope** — добавленные и вырезанные фичи
  отражаются в спецификации.
- **Коммить спецификацию** — она живёт в VCS рядом с кодом.
- **Ссылайся на спецификацию в PR** — давай ссылку на раздел, который
  реализует PR.

## Распространённые оправдания

| Оправдание | Реальность |
|---|---|
| «Это просто, мне не нужна спецификация» | Простые задачи не требуют *длинной* спецификации, но критерии приёмки нужны. Двух строк достаточно. |
| «Напишу спецификацию после кода» | Это документирование, а не проектирование. Смысл — внести ясность **до** кода. |
| «Спецификация замедлит нас» | 15 минут на спеку сэкономят часы переделок. |
| «Требования всё равно изменятся» | Поэтому спецификация — живой документ. Устаревшая лучше, чем отсутствующая. |
| «Пользователь знает, чего хочет» | Даже у понятных запросов есть скрытые предположения. Спецификация их выявляет. |

## Красные флаги

- Начало написания кода без зафиксированных требований.
- Вопрос «Может, просто начать писать код?» до уточнения «что значит
  задача выполнена».
- Реализация фич, не упомянутых в спецификации.
- Принятие архитектурных решений без их документирования.
- Пропуск спецификации, потому что «и так очевидно».

## Проверка

Перед переходом к реализации подтверди:

- [ ] Спецификация охватывает все шесть ключевых областей (или три —
      для облегчённого варианта).
- [ ] Человек изучил и утвердил спецификацию.
- [ ] Критерии успеха конкретны и проверяемы.
- [ ] Границы (Всегда / Сначала спроси / Никогда) определены.
- [ ] Спецификация сохранена в файл в репозитории.
