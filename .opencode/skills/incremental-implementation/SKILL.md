# Инкрементальная реализация

## Обзор

Строй ПО по одному **вертикальному слайсу** за раз. Каждый слайс даёт
работающий end-to-end результат, проверяется и оставляет систему в
отгружаемом состоянии. Никогда не пиши код, который ещё ничего не
делает — никакого каркаса, заглушек, placeholder-ов «на будущее».

Этот скилл — имплементационная пара к
[planning-and-task-breakdown](../planning-and-task-breakdown/SKILL.md).
Планирование определяет *какие* слайсы существуют; этот скилл
определяет *как* построить каждый из них, не создавая клубок.

## Когда использовать

- Реализация любой задачи из `tasks/todo.md`
- Добавление фичи в существующий код
- Изменение, затрагивающее более одного слоя (схема + API + UI и т. п.)
- Когда ловишь себя на желании «подготовить почву» перед реальной работой
- Когда задача кажется больше, чем одна сфокусированная сессия

**Когда НЕ использовать:** Правки в одну строку, исправление опечаток
или изменения, где вся реализация очевидна и самодостаточна.

## Слайс

**Слайс** — это тончайший end-to-end путь, который даёт работающий
результат, наблюдаемый пользователем или вызывающим кодом.

- **Вертикальный, не горизонтальный.** Слайс затрагивает все слои,
  нужные для результата — но только тончайший путь через каждый. Он не
  строит «всю схему» или «все API».
- **Полный, не частичный.** После слайса фича работает end-to-end хотя
  бы по одному пути. Она может ещё не обрабатывать все граничные
  случаи — но ничего не осталось полу-связанным.
- **Маленький.** Один слайс должен быть реализуем, тестируем и
  проверяем в одной сфокусированной сессии. Если не получается — это
  два слайса.

### Примеры

**Плохо (горизонтально):**
```
Слайс 1: Полная схема БД для users, tasks, projects
Слайс 2: Все API-эндпоинты для этих сущностей
Слайс 3: Все UI-компоненты
Слайс 4: Связать всё вместе
```

Каждый слайс оставляет систему неработающей. Интеграция происходит в
конце и она болезненна.

**Хорошо (вертикально):**
```
Слайс 1: Пользователь может зарегистрироваться (таблица users + эндпоинт регистрации + форма)
Слайс 2: Пользователь может войти (колонки auth + эндпоинт входа + форма)
Слайс 3: Пользователь может создать задачу (таблица tasks + эндпоинт + форма)
Слайс 4: Пользователь может видеть список задач (запрос + эндпоинт + отображение)
```

Каждый слайс даёт работающую фичу, которой реально можно пользоваться.

## Tracer Bullet

Tracer bullet — это слайс, который попадает в цель: он идёт end-to-end,
от внешнего seam до слоя хранения и обратно, даже если код по пути
минимален.

Первый слайс любой фичи должен быть tracer bullet. Он:

- подтверждает, что архитектура работает,
- заставляет все точки интеграции быть подключёнными сразу,
- вскрывает упущенные предположения до того, как ты начнёшь строить
  поверх.

Tracer bullet — это **не** каркас. Каркас — это структура без поведения.
Tracer bullet делает что-то реальное, просто минимально.

## Основной процесс

### 1. Выбери ровно один слайс

Прочитай `tasks/todo.md`. Возьми первую невыполненную задачу. Не начинай
вторую. Не пытайся «заодно быстро починить» соседнюю проблему.

Если задача кажется слишком большой, раздели её до начала. Разделение
дёшево; восстановление из полу-построенного клубка — нет.

### 2. Назови seam

Перед тем как писать что-либо, зафиксируй:

- внешний seam, на котором тестируется слайс (см. [tdd](../tdd/SKILL.md)),
- слои, которые затрагивает слайс,
- как выглядит «готово» для этого слайса — одно предложение.

Подтверди seam с пользователем, если этого требует
[tdd](../tdd/SKILL.md). Не продолжай без определённого seam.

### 3. Сначала напиши падающий тест

Следуй [tdd](../tdd/SKILL.md). Тест описывает результат на seam:

```
"пользователь может зарегистрироваться с валидным email и паролем"
```

Не «эндпоинт регистрации вызывает репозиторий users». Тестируй
поведение, не реализацию.

### 4. Реализуй минимум для прохождения

Пиши минимальный код по пути от seam до хранилища и обратно. Не меньше —
тест должен пройти. Не больше — следующий тест вытянет следующую строку
кода.

Сопротивляйся соблазну:

- добавить валидацию для случаев, которые тест не покрывает,
- добавить конфигурацию для окружений, которых ещё нет,
- извлечь абстракцию для второго вызывающего, которого ещё нет.

### 5. Останови и проверь end-to-end

После прохождения теста:

- запусти полный набор тестов (не только свой),
- запусти сборку,
- проверь слайс вручную, если seam user-facing.

Система должна быть отгружаемой после каждого слайса. Если нет — ты не
режешь вертикально.

### 6. Рефакторинг — только после green

Рефакторинг не является частью TDD-цикла (см. [tdd](../tdd/SKILL.md)).
Это явный проход **после** того, как слайс работает, и только когда:

- следующий слайс будет проще при другой структуре,
- текущая структура имеет очевидный запах (см.
  [code-review](../code-review/SKILL.md)),
- можно отрефакторить без изменения поведения.

Если ни то, ни другое, ни третье не верно — оставь код в покое и
переходи к следующему слайсу.

### 7. Отметь задачу выполненной

Обнови `tasks/todo.md`: `[x]`.

Закоммить слайс как одно атомарное изменение (см.
[git-conventions](../git-conventions/SKILL.md)). Один слайс, один коммит.

### 8. Следующий слайс

Вернись к шагу 1. Возьми следующую невыполненную задачу.

## Антипаттерны

Каждая строка кода должна вытягиваться из теста, который существует
**прямо сейчас**. Если строка не востребована существующим тестом — не
пиши её.

- **Горизонтальный слайсинг** — построение всего одного слоя до
  следующего. Ломает интеграцию в конце.
- **Каркас заранее** — структура файлов, типы или конфигурация для фич,
  которых нет.
- **Спекулятивная обобщённость** — абстракции под воображаемые будущие
  требования.
- **Спекулятивные фичи** — поведение, которое спецификация не
  запрашивала.
- **Placeholder-типы** — пустой тип с полями «заполним позже».
- **Заглушки и моки в production-коде** — `TODO: implement` или
  функция, возвращающая `null`.
- **Закомментированный код** — либо он нужен, либо нет.
- **Молчаливая частичная реализация** — обработчик, покрывающий happy
  path и возвращающий `500` для всего остального без объявления этого в
  объёме задачи.
- **Молчаливый scope creep** — «заодно я ещё...». Либо в задаче, либо
  нет.
- **Big-bang интеграция** — момент, когда всё связывается в конце.
- **Полу-завершённые задачи** — оставить задачу незаконченной и начать
  следующую.
- **Тесты, написанные задним числом** — «добавлю тесты, когда
  заработает». К тому моменту ты уже написал непокрытый код.

## Распространённые оправдания

| Оправдание | Реальность |
|---|---|
| «Быстрее построить всё сразу и протестировать в конце» | Конец — это место, где появляется клубок. Инкрементально быстрее, потому что ты никогда не дебажишь больше одного слайса за раз. |
| «Добавлю тесты после реализации» | Тесты, написанные задним числом, описывают что код делает, а не что должен. Они пройдут по построению. |
| «Мне нужна эта абстракция для следующего слайса» | Тогда добавь её в следующем слайсе, когда будет второй use case для дизайна. |
| «Задача почти готова — я просто закончу её и начну следующую в том же изменении» | Закончить = закоммичено и отмечено. Начать следующую в том же коммите ломает атомарность. |
| «Эта дополнительная валидация очевидна и дёшева» | Если тест её не требует — это scope creep. Она будет востребована будущим слайсом. |
| «Я просто подготовлю почву для всей фичи сразу» | Почва, которая ничего не делает — это каркас. Каркас гниёт до использования. |

## Красные флаги

- Файлы, созданные и пока ничего не делающие.
- Заглушки, placeholders или `TODO:`-комментарии, добавленные в ходе
  реализации.
- Несколько задач из `tasks/todo.md` в одном коммите.
- Тесты, добавленные «позже» или «после связывания».
- Система сломана между двумя слайсами.
- Слайс, который нельзя описать одним предложением результата.
- Слайс, занимающий больше одной сфокусированной сессии.
- Абстракция с одним вызывающим.

## Проверка

После каждого слайса:

- [ ] Слайс даёт работающий end-to-end путь, наблюдаемый пользователем
      или вызывающим кодом.
- [ ] Падающий тест написан первым (см. [tdd](../tdd/SKILL.md)).
- [ ] Написан только код, нужный для прохождения теста.
- [ ] Никаких заглушек, placeholders или `TODO:`-маркеров не осталось.
- [ ] Никаких абстракций с одним вызывающим.
- [ ] Никакого поведения, которого не запрашивает спецификация.
- [ ] Полный набор тестов проходит.
- [ ] Сборка успешна.
- [ ] Система работает end-to-end (не только юнит-тесты).
- [ ] `tasks/todo.md` помечает эту задачу как `[x]`.
- [ ] Изменение атомарно — один слайс, один коммит.
