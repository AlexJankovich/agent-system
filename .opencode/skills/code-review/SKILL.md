# Code Review

Двухосевое ревью диффа между `HEAD` и фиксированной точкой, которую
указывает пользователь:

- **Standards** — соответствует ли код документированным стандартам
  репозитория, пяти измерениям качества и smell-baseline?
- **Spec** — точно ли реализует код исходный issue / PRD / спеку?

Оси запускаются как **параллельные субагенты**, чтобы не загрязнять
контекст друг друга. Этот скилл агрегирует их находки.

Трекер задач должен быть настроен — если `docs/agents/issue-tracker.md`
отсутствует, сначала настрой его.

## Исполнение в OpenCode V2

Вложенность субагентов в V2 по умолчанию равна **1**, и у субагента
`reviewer` в `.opencode/agents/reviewer.md` стоит
`action: "subagent", effect: "deny"`. Это значит, что **fan-out по
двум осям выполняет родитель** (`build`), запуская **двух `reviewer`
параллельно** одним сообщением, каждому со своей осью в `prompt`.

Если скилл загружен самим `reviewer` (единичный вызов), он выполняет
обе оси **последовательно**: сначала Standards, затем Spec.

Дальнейшее описание процесса описывает логику ревью; механику запуска
определяет вызывающая сторона.

## Процесс

### 1. Зафиксировать точку сравнения

Фиксированная точка — то, что назвал пользователь: SHA коммита, имя
ветки, тег, `main`, `HEAD~5` и т. п. Если не указал — спроси.

Один раз зафиксируй команду диффа: `git diff <fixed-point>...HEAD`
(три точки, сравнение с merge-base). Также запомни список коммитов
через `git log <fixed-point>..HEAD --oneline`.

Проверь, что точка разрешается (`git rev-parse <fixed-point>`), а дифф
не пустой. Плохая ссылка или пустой дифф должны падать здесь — не
внутри двух параллельных субагентов.

### 2. Определить источник спеки

Ищи исходную спеку в таком порядке:

1. Ссылки на issue в сообщениях коммитов (`#123`, `Closes #45`) —
   получи через `docs/agents/issue-tracker.md`.
2. Путь, переданный пользователем как аргумент.
3. Файл PRD/спеки в `docs/`, `specs/` или `.scratch/`, совпадающий с
   именем ветки или фичей.
4. Если ничего не найдено — спроси пользователя, где спека. Если её
   нет, ось **Spec** пропускается и сообщает «спека недоступна».

### 3. Определить источники стандартов

Всё в репозитории, что документирует, как писать код — например,
`CODING_STANDARDS.md` или `CONTRIBUTING.md`.

Поверх того, что документирует репозиторий, ось Standards всегда несёт
**пять измерений качества** и **smell-baseline** ниже.

#### Пять измерений качества

- **Корректность (Correctness)** — делает ли код то, что заявляет?
  Обработаны ли граничные случаи (null, пустой ввод, границы)? Есть
  ли обработка ошибок, а не только happy path? Проходят ли тесты и
  проверяют ли они то, что нужно? Нет ли off-by-one, race condition,
  несогласованного состояния?
- **Читаемость (Readability)** — поймёт ли другой инженер (или агент)
  код без объяснений автора? Имена ясны и согласованы с проектными
  соглашениями (никаких `temp`, `data`, `result` без контекста)?
  Управляющий поток прост? Нет ли «умных» мест, которые стоит
  упростить? Можно ли решить задачу меньшим числом строк? Оправдана
  ли сложность абстракций (нет обобщения до третьего случая)?
- **Архитектура (Architecture)** — вписывается ли изменение в
  существующие паттерны или вводит новый? Если новый — оправдан?
  Границы модулей чистые? Есть ли дублирование для извлечения?
  Зависимости направлены правильно (без циклов)? Уровень абстракции
  верный?
- **Безопасность (Security)** — см. `references/security-checklist.md`.
  Валидируется ли пользовательский ввод и очищается ли он? Нет ли
  секретов в коде, логах, VCS? Проверяется ли auth/authz? SQL-запросы
  параметризованы? Вывод кодируется (XSS)? Внешние источники (API,
  логи, пользовательский контент, конфиг) обрабатываются как
  недоверенные?
- **Производительность (Performance)** — см.
  `references/performance-checklist.md`. Нет ли N+1? Неограниченных
  циклов или загрузок? Синхронных операций, которым нужен async?
  Лишних ререндеров в UI? Пагинации для списочных API? Больших
  объектов в горячих путях?

#### Smell Baseline

См. `references/smell-baseline.md`. Он несёт Fowler-овский smell-
baseline, применимый даже когда репозиторий ничего не документирует.
Два правила его ограничивают: репозиторий переопределяет, а каждый
smell — это суждение, а не жёсткое нарушение.

#### Размер изменения

Предпочитай небольшие, сфокусированные изменения.

```
~100 изменённых строк  → Хорошо. Просматривается за один проход.
~300 изменённых строк  → Допустимо, если это одно логическое изменение.
~1000 изменённых строк → Слишком много. Разбей.
```

**Одно изменение** = самодостаточная модификация, решающая одну
задачу, включая связанные тесты, и оставляющая систему рабочей после
себя. Это один слайс функциональности, а не вся фича.

Способы разбить: **стек** (строить на маленьком изменении),
**по группам файлов** (разнести по ревьюерам), **горизонтально**
(сначала общая инфраструктура, затем потребители), **вертикально**
(маленькие end-to-end слайсы).

Большие изменения допустимы только для полного удаления файлов и
механических рефакторингов, где ревьюер проверяет намерение, а не
каждую строку.

**Отделяй рефакторинг от функциональных изменений.** Изменение,
которое рефакторит и добавляет новое поведение, — это два изменения.

### 4. Классифицировать каждую находку

Каждой находке присваивается префикс severity:

| Префикс | Значение | Действие автора |
|---|---|---|
| *(нет)* | Обязательное изменение | Исправить до merge |
| **Critical:** | Блокирует merge | Безопасность, потеря данных, сломанная функциональность |
| **Nit:** | Мелкое замечание | Можно игнорировать |
| **Optional:** / **Consider:** | Рекомендация | Стоит рассмотреть |
| **FYI** | Информация | Действие не требуется |

Так обязательные замечания отличаются от необязательных.

### 5. Запустить обе оси

В OpenCode V2 fan-out выполняет **вызывающая сторона** (обычно `build`),
запуская двух `reviewer` одним сообщением, каждому со своей осью.

**Промпт для оси Standards** — включи:

- полную команду диффа и список коммитов;
- список файлов-источников стандартов из шага 3, **плюс пять измерений
  качества, smell-baseline и правила размера изменения** целиком;
- бриф: «Отчитайся — по файлу/хунку, где релевантно — (a) о каждом
  месте, где дифф нарушает документированный стандарт: процитируй
  стандарт (файл + правило); (b) о любом нарушении пяти измерений
  качества: назови измерение и процитируй хунк; (c) о любом smell из
  baseline: назови его и процитируй хунк. Присвой каждой находке
  префикс severity (Critical / Nit / Optional / FYI). Различай жёсткие
  нарушения и суждения — нарушения документированных стандартов могут
  быть жёсткими, но базовые smells — всегда суждения; документированный
  стандарт репозитория переопределяет baseline. Пропускай то, что
  проверяется инструментами. До 400 слов.»

**Промпт для оси Spec** — включи:

- команду диффа и список коммитов;
- путь или полученное содержимое спеки;
- бриф: «Отчитайся: (a) о требованиях спеки, которые отсутствуют или
  реализованы частично; (b) о поведении в диффе, которое не было
  запрошено (scope creep); (c) о требованиях, которые выглядят
  реализованными, но реализация выглядит неверной. Цитируй строку
  спеки для каждой находки. Присвой каждой находке префикс severity
  (Critical / Nit / Optional / FYI). До 400 слов.»

Если спека отсутствует, пропусти ось Spec и отметь это в финальном
отчёте.

### 6. Агрегировать

Представь два отчёта под заголовками `## Standards` и `## Spec`,
дословно или слегка вычищенными. **Не сливай и не переранжируй**
находки — две оси намеренно разделены (см. «Почему две оси»).

Заверши однострочной сводкой: общее число находок по каждой оси и
худшая проблема **внутри каждой оси**. Не выбирай одного победителя
между осями.

### 7. Опционально: autofix

Если в вызове было слово `autofix`, после агрегации примени только
находки категории «стоит исправить сейчас», выполни сфокусированную
валидацию и подведи итог. Не применяй необязательные улучшения без
явного запроса.

Без `autofix` спроси перед применением исправлений. Спрашивая, выдай
компактное нумерованное меню, чтобы пользователь ответил цифрой:

```
Ответь [1], [2] или введи дальнейшие инструкции:
[1] Применить только исправления, которые стоит сделать сейчас.
[2] Применить исправления, которые стоит сделать сейчас, плюс необязательные улучшения.
```

## Почему две оси

Изменение может пройти одну ось и провалить другую:

- Код, соблюдающий все стандарты, но реализующий не то →
  **Standards pass, Spec fail.**
- Код, делающий ровно то, что просил issue, но ломающий соглашения →
  **Spec pass, Standards fail.**

Разделение отчётов не даёт одной оси маскировать другую.
