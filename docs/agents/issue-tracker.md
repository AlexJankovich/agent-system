# Трекер задач (Issue Tracker)

Этот документ описывает, как агенты получают содержимое issue, PR и
связанных спецификаций из трекера задач проекта. На него ссылается
скилл `code-review` (шаг 2 «Определить источник спеки»), и его же
могут использовать `build` и `worker`, когда задача привязана к issue.

## Настроенный трекер

**GitHub**. Доступ — двумя способами:

1. `gh` CLI (предпочтительно).
2. MCP-сервер `github` (см. `.opencode/opencode.jsonc`).

Предпочитай `gh` CLI: он проще, не потребляет контекст MCP и не зависит
от состояния MCP-соединения. К MCP обращайся, только если `gh` даёт
ошибку авторизации или сетевой таймаут.

Все команды ниже выполняются через инструмент `shell`. Политика
`opencode.jsonc` разрешает `gh issue create` и `gh pr create` только
после подтверждения; **чтение** issue и PR разрешено без запроса.

## Как получить issue

По номеру:

```bash
gh issue view <number> --json \
  number,title,body,state,labels,assignees,comments,url
```

Для читаемого вывода без JSON:

```bash
gh issue view <number>
```

Поля, которые нужны агенту:

- `number`, `title` — идентификация.
- `body` — основное требование или описание бага.
- `labels` — тип (bug / feature / chore) и приоритет.
- `state` — open / closed (учитывай при трактовке актуальности).
- `comments` — обсуждение может уточнять или отменять исходное
  требование.

Если issue содержит чек-лист приёмочных критериев
(`- [ ] ...` или `## Acceptance criteria`), **цитируй его целиком** —
это основной вход для оси Spec в `code-review`.

## Как получить PR

По номеру:

```bash
gh pr view <number> --json \
  number,title,body,state,headRefName,baseRefName,url,commits,files
```

Для получения диффа PR без checkout:

```bash
gh pr diff <number>
```

Для получения списка связанных issue из тела PR (обычно строки вида
`Closes #123`, `Fixes #45`):

```bash
gh pr view <number> --json body --jq '.body' \
  | grep -oE '(Closes|Fixes|Resolves) #[0-9]+'
```

## Как найти PR по ветке или коммиту

По текущей ветке:

```bash
gh pr view --json number,title,body,url
```

По коммиту (если он привязан к PR):

```bash
gh pr list --search "<sha>" --state all --json number,title,url
```

## Как распознать ссылки на issue в коммитах

История коммитов часто содержит ссылки на issue. Ищи в сообщениях
коммитов и в заголовках PR такие паттерны:

- `#123` — прямая ссылка.
- `Closes #123`, `Fixes #123`, `Resolves #123` — закрывающие ссылки.
- `Refs #123` — не закрывает, но связана.

Команда для извлечения всех ссылок из диапазона коммитов:

```bash
git log <fixed-point>..HEAD --oneline \
  | grep -oE '#[0-9]+' \
  | sort -u
```

Для каждой найденной ссылки номер — это номер issue в GitHub.

## Что возвращать вызывающему агенту

Когда `code-review` (или другой скилл) запрашивает спеку по issue,
верни:

```
Issue: #<number> — <title>
URL: <url>
State: <open|closed>
Labels: <labels>

## Тело issue
<body>

## Приёмочные критерии
<извлечённый чек-лист, если есть>

## Комментарии, меняющие требование
<только те, где требование уточняется или отменяется>
```

Не дампируй весь JSON и все комментарии — выбери то, что относится к
реализации. Если комментарии не меняют требование, опусти их.

## Если ничего не найдено

Если в коммитах нет ссылок, в аргументах вызова нет пути и в
`docs/`, `specs/`, `.scratch/` нет файла PRD, совпадающего с фичей —
**спроси пользователя, где спека**. Если пользователь говорит, что
спеки нет, ось Spec в `code-review` пропускается, а в финальном отчёте
отмечается «спека недоступна».

Не придумывай спеку и не реконструируй её по диффу — это создаёт
ложные требования.

## Если трекер недоступен

Если `gh` не аутентифицирован (`gh auth status` возвращает ошибку) —
сообщи пользователю, что нужно выполнить `gh auth login`, и не пытайся
продолжить ревью без спеки. Если MCP-сервер `github` не поднят, но
`gh` работает — используй `gh`.

## Не входит в этот документ

- **Публикация** изменений (создание веток, коммитов, PR) — см. скилл
  `pull-request` и `git-conventions`.
- **Создание** issue из разговорного описания бага — см. периферийный
  скилл `qa`.
- **Политики прав** для shell-команд — см. `.opencode/opencode.jsonc`.
